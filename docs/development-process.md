# Процесс разработки FleetControl

## 1. Назначение документа

Документ описывает принятый в проекте FleetControl процесс разработки программного обеспечения: управление работами в Jira, использование Git и GitHub, стратегию ветвления, проведение Code Review и тестирования, применение CI, управление версиями и подготовку релизов.

FleetControl представляет собой демонстрационную информационную систему управления автопарком такси. Проект используется для отработки полного жизненного цикла разработки программного обеспечения — от постановки задачи до выпуска версии.

В учебной реализации разработка выполняется одним человеком, однако процесс построен так, чтобы соответствовать командной разработке: задачи проходят отдельные стадии анализа, реализации, проверки, тестирования и выпуска.

## 2. Используемые инструменты

В проекте используются следующие инструменты:

- **Jira Cloud** — управление требованиями, задачами, дефектами, спринтами и версиями;
- **Git** — система контроля версий;
- **GitHub** — хранение репозитория и проведение Pull Request;
- **GitHub Actions** — автоматизированное выполнение тестов;
- **Node.js** и **Express** — серверное приложение;
- **PostgreSQL** — система управления базой данных;
- **Jest** и **Supertest** — автоматизированное тестирование;
- **Docker** и **Docker Compose** — контейнеризация и воспроизводимое развёртывание.

Основной репозиторий проекта:

`fleet_control`

## 3. Управление работами в Jira

### 3.1 Иерархия работ

В проекте используются следующие типы рабочих элементов:

- **Epic** — крупное функциональное или инфраструктурное направление;
- **Story** — пользовательский или бизнес-сценарий;
- **Task** — самостоятельная техническая или организационная работа;
- **Bug** — обнаруженный дефект;
- **Subtask** — часть родительской задачи, не являющаяся самостоятельной единицей верхнего уровня.

Примеры Epic проекта:

- управление автопарком;
- эксплуатация и назначение автомобилей;
- техническое обслуживание и ремонт;
- тарифы и финансовые операции;
- инфраструктура и выпуск версий.

Для крупных Story допускается декомпозиция на самостоятельные Task. Такие задачи связываются с Story специальным типом связи **«Реализация»**:

- Task `реализует` Story;
- Story `реализуется задачей` Task.

Такой подход применяется, когда дочерняя работа должна иметь собственный жизненный цикл, оценку, ветку и Pull Request.

Subtask используется для более тесно связанной работы внутри одной родительской задачи. Например, задача подготовки документации разделена на подзадачи описания процесса разработки и процесса развёртывания.

## 4. Workflow задачи

Для Task и Bug применяется следующий основной workflow:

`To Do → In Progress → In Review → Testing → Ready for Release → Done`

Назначение статусов:

### To Do

Работа создана и запланирована, но реализация ещё не начата.

### In Progress

Разработка или выполнение задачи начато.

Создание Git-ветки, содержащей ключ Jira-задачи, может автоматически переводить задачу в этот статус.

### In Review

Реализация завершена и создан Pull Request.

На данной стадии выполняется Code Review.

### Testing

Изменения прошли первичную проверку и переданы на тестирование.

На стадии Testing выполняются автоматизированные и, при необходимости, ручные проверки.

### Ready for Release

Изменения протестированы и интегрированы в соответствующую интеграционную ветку, однако ещё не выпущены пользователям.

### Done

Изменения входят в фактически выпущенную версию.

Переход в Done выполняется после выпуска соответствующей Jira Version.

---

## 5. Workflow агрегирующей Story

Для Story, декомпозированной на несколько самостоятельных Task, используется упрощённый workflow:

`To Do → In Progress → Testing → Ready for Release → Done`

Стадия `In Review` на уровне агрегирующей Story не используется, поскольку Code Review выполняется отдельно для каждой технической Task.

Story может автоматически переходить:

- в `In Progress`, когда начинается реализация связанной Task;
- в `Testing`, когда все связанные задачи реализации достигли `Ready for Release`.

После функциональной приёмки Story переводится в `Ready for Release`.

---

## 6. Плановые и фактические даты

Для задач используются плановые и фактические даты.

Плановые поля:

- Start date — планируемая дата начала;
- Due date — планируемая дата завершения.

Фактические поля:

- Actual Start — реальное начало выполнения;
- Actual End — реальное завершение.

Actual Start заполняется при первом переходе задачи в `In Progress`.

Actual End фиксируется при достижении `Ready for Release`.

Плановые даты не заменяются фактическими, поскольку используются как исходный baseline для сравнения плана и факта.

Для анализа может дополнительно использоваться поле отклонения от срока в рабочих днях.

## 7. Стратегия ветвления Git

В проекте используются три постоянные ветки.

### 7.1 `main`

`main` содержит только актуальную выпущенную production-версию приложения.

Изменения не разрабатываются непосредственно в `main`.

Попадание изменений в `main` происходит только в результате подготовки и выпуска версии.

### 7.2 `develop`

`develop` является интеграционной веткой следующей функциональной версии приложения.

В неё объединяются новые возможности, разрабатываемые в `feature/*`.

Пример:

```text
feature/FLEET-13-return-replacement-vehicle
                ↓
             develop
```

### 7.3 `maintenance`

`maintenance` предназначена для сопровождения текущей production-версии.

В неё интегрируются исправления дефектов, обнаруженных в версии, находящейся в `main`.

Пример:

```text
bugfix/FLEET-33-invalid-id-validation
                ↓
            maintenance
```

Таким образом, разработка следующей функциональной версии и сопровождение текущей production-версии могут выполняться параллельно.

---

## 8. Временные ветки

### 8.1 `feature/*`

Используются для реализации новой функциональности.

Пример:

```text
feature/FLEET-20-docker-compose
```

Создаются от `develop` и после завершения работы объединяются обратно в `develop`.

### 8.2 `bugfix/*`

Используются для исправления обычных дефектов текущей production-версии.

Пример:

```text
bugfix/FLEET-34-active-driver-validation
```

Создаются от актуальной `maintenance` и объединяются обратно в `maintenance`.

### 8.3 `release/*`

Создаются для подготовки конкретной версии к выпуску.

Примеры:

```text
release/0.2.1
release/1.0.0
```

В release-ветке допускаются изменения, непосредственно связанные с подготовкой версии:

- изменение номера версии;
- актуализация release-specific тестов;
- исправление ошибок, обнаруженных при финальной проверке;
- подготовка релизной конфигурации.

После успешной проверки release-ветка объединяется в `main`.

### 8.4 `hotfix/*`

Предназначены для экстренного исправления критического production-дефекта, который необходимо выпустить немедленно, не ожидая обычного patch-релиза.

В штатном процессе большинство дефектов проходят через `bugfix/* → maintenance`.

## 9. Жизненный цикл функциональной задачи

Типовой процесс разработки новой функциональности:

```text
Jira Task / Story
        ↓
feature/*
        ↓
локальная разработка
        ↓
автоматизированные тесты
        ↓
Pull Request в develop
        ↓
Code Review
        ↓
Testing
        ↓
merge в develop
        ↓
Ready for Release
```

Ключ Jira-задачи включается в название ветки и сообщения commit.

Пример:

```text
feature/FLEET-13-return-replacement-vehicle
```

Commit:

```text
FLEET-13 Implement replacement vehicle return
```

Это обеспечивает связь Jira с GitHub и позволяет отслеживать реализацию задачи.

## 10. Жизненный цикл исправления дефекта

Дефекты регистрируются в Jira как Bug.

Для Bug фиксируются:

- описание проблемы;
- ожидаемое поведение;
- фактическое поведение;
- версия, в которой дефект обнаружен;
- версия, в которой планируется исправление.

Пример:

```text
Affects Version: 0.2.0
Fix Version: 0.2.1
```

Исправление выполняется следующим образом:

```text
Bug
 ↓
bugfix/*
 ↓
регрессионный тест, воспроизводящий дефект
 ↓
исправление
 ↓
автоматизированное и ручное тестирование
 ↓
Pull Request в maintenance
 ↓
merge
 ↓
Ready for Release
```

Регрессионный тест создаётся до или одновременно с исправлением, чтобы исключить повторное появление дефекта.

В версии `0.2.1` таким образом были исправлены:

- некорректная обработка строковых и дробных идентификаторов;
- возможность назначения подменного автомобиля неактивному водителю.

## 11. Pull Request и Code Review

Изменения не объединяются напрямую в интеграционные ветки.

Основные направления Pull Request:

```text
feature/* → develop
bugfix/* → maintenance
release/* → main
```

PR содержит:

- краткое описание реализованного изменения;
- перечень основных изменений;
- сведения о тестировании;
- ключ Jira-задачи;
- версию, для которой предназначено изменение.

Перед merge проверяется:

- соответствие реализации требованиям задачи;
- корректность кода;
- наличие тестов;
- результат CI;
- отсутствие нежелательных изменений.

После merge временная ветка удаляется.

## 12. Автоматизация Jira и GitHub

Jira интегрирована с GitHub.

Используются автоматические действия:

- создание ветки по задаче переводит её в `In Progress`;
- создание Pull Request переводит задачу в `In Review`;
- после merge задача может переходить в `Ready for Release`;
- commit с ключом Jira связывается с задачей;
- при выпуске Jira Version задачи соответствующей версии переводятся из `Ready for Release` в `Done`.

Автоматизация учитывает целевую интеграционную ветку:

- `develop` для функциональной разработки;
- `maintenance` для исправлений production-версии.

Для предотвращения ложного изменения статусов учитывается связь между Jira-key и source branch.

## 13. Автоматизированное тестирование

В проекте используются Jest и Supertest.

Тестируются:

- endpoint `/health`;
- получение списка автомобилей;
- получение списка водителей;
- назначение подменного автомобиля;
- проверка некорректных идентификаторов;
- проверка статуса водителя;
- возврат подменного автомобиля;
- негативные сценарии API.

Запуск локально:

```bash
npm test
```

Для CI:

```bash
npm run test:ci
```

Регрессионные тесты сохраняются в репозитории и выполняются при последующих изменениях проекта.

---

## 14. Ручное тестирование

Помимо автоматизированных тестов выполняются ручные проверки API на реальной PostgreSQL.

Ручные тест-кейсы хранятся в каталоге:

```text
docs/test-cases/
```

Для версии `0.2.0` были проведены:

- функциональная проверка назначения подменного автомобиля;
- расширенное негативное тестирование API.

Именно в ходе негативного тестирования были обнаружены production-дефекты, которые вошли в patch-релиз `0.2.1`.

## 15. Continuous Integration

Для CI используется GitHub Actions.

Workflow запускается для Pull Request и push в основные интеграционные ветки:

```text
develop
maintenance
main
```

CI выполняет:

1. checkout репозитория;
2. настройку Node.js;
3. установку зависимостей через `npm ci`;
4. запуск `npm run test:ci`.

Merge выполняется только после успешного прохождения автоматизированных тестов.

## 16. Управление версиями

В проекте используется Semantic Versioning:

```text
MAJOR.MINOR.PATCH
```

Примеры:

```text
0.1.0
0.2.0
0.2.1
1.0.0
```

Назначение компонентов:

- `MAJOR` — несовместимые или принципиально значимые изменения;
- `MINOR` — новая функциональность с сохранением совместимости;
- `PATCH` — исправления дефектов без добавления значимой новой функциональности.

Для каждой выпускаемой версии используются:

- Jira Version;
- release-ветка;
- Git tag;
- GitHub Release.

Пример тега:

```text
v0.2.1
```

## 17. Подготовка функционального релиза

Новая функциональная версия формируется из `develop`.

Процесс:

```text
feature/*
   ↓
develop
   ↓
release/X.Y.0
   ↓
финальное тестирование
   ↓
main
   ↓
tag
   ↓
GitHub Release
   ↓
Jira Version Released
```

Перед установкой тега проверяется, что `main` действительно содержит правильную версию приложения и все тесты проходят успешно.

---

## 18. Подготовка patch-релиза

Исправления production-версии интегрируются в `maintenance`.

Процесс:

```text
bugfix/*
   ↓
maintenance
   ↓
release/X.Y.Z
   ↓
финальное тестирование
   ↓
main
   ↓
tag
   ↓
GitHub Release
   ↓
Jira Version Released
```

Такой процесс использовался для выпуска `0.2.1`.

Версия `0.2.1` включала исправления дефектов, обнаруженных после выпуска `0.2.0`.

---

## 19. Синхронизация исправлений с будущей версией

После patch-релиза исправления production-версии должны попасть в дальнейшую разработку.

Если этого не сделать, ранее исправленный дефект может повторно появиться в следующей функциональной версии.

Поэтому изменения из production-линии переносятся в `develop` через отдельный Pull Request.

При этом учитывается, что код в `develop` может уже отличаться от production-версии.

Возможны два случая:

1. изменения совместимы — выполняется обычный merge;
2. архитектура кода изменилась — выполняется forward-port, то есть переносится не обязательно тот же фрагмент кода, а исправленное поведение.

После переноса обязательно запускаются регрессионные тесты.

## 20. Хранение артефактов

Артефакты разработки хранятся в нескольких системах.

### Jira

Хранит:

- Epic;
- Story;
- Task;
- Bug;
- Subtask;
- Sprint;
- Version;
- статусы;
- сроки;
- связи между задачами.

### GitHub

Хранит:

- исходный код;
- историю commit;
- ветки;
- Pull Request;
- Git tags;
- GitHub Releases;
- CI workflow.

### Репозиторий

Вместе с исходным кодом версионируются:

- миграции БД;
- seed-скрипты;
- автоматизированные тесты;
- ручные test cases;
- Docker-конфигурация;
- документация разработки;
- документация развёртывания.

Такой подход позволяет связать требования, реализацию, тестирование и конкретную версию программного продукта.
